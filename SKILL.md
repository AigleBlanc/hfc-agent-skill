# HFC Agent Skill (drop-in project skill — Claude Code)

Copy this folder anywhere as **`.claude/skills/hfc-agent-skill/`** (Claude Code discovers skills there), then configure **`config.json`** at this skill's root with four directories: **Input Data Directory** (survey microdata), **Media Folder Directory** (optional — audio/image attachments; reserved for future use, no check currently reads it), **HFC Output Directory** (a OneDrive-synced folder for the shared `issue_tracking.xlsx`), and **Code Output Directory** (a git working copy the user manages themselves — World Bank practice prefers versioned code/config output; this skill only ever writes plain files there, never runs git). A fifth, optional key, **Main Tracking Filename**, names the shared tracking file if you don't want the `issue_tracking.xlsx` default (see `references/issue_tracking_schema.md`). There is no "survey project root" concept — the skill never searches for data, and the built product is decoupled from wherever the raw data lives. Skill tree map: `hfc/structure.html` (generated), deps: `install.R`.

Supporting files resolve via `${CLAUDE_SKILL_DIR}` (this skill directory); every script reads its paths from `config.json`, not from CLI arguments:

```bash
Rscript .claude/skills/hfc-agent-skill/scripts/run_setup_build.R
Rscript "${CLAUDE_SKILL_DIR}/scripts/run_setup_build.R"
```

**Built product** (`config/`, `instruments/`, `outputs/`, `code/` — with `code/checks/` and `code/resolutions/`) always lands under **`hfc/`** inside the configured Code Output Directory. `issue_tracking.xlsx` itself lives entirely in the configured HFC Output Directory (required — see A0), not under `hfc/`; it has two sheets, **Tracking** (the findings) and **Completion** (a respondent-level copy of the roster, or of the surveyed IDs when there's no roster, plus `submitted`, `completed` and `reason_no_completion` — see `references/issue_tracking_schema.md`). `hfc/structure.html` and the report open together at the very end (A4), for the final Review & Approve gate — see Pipeline A below.

Two pipelines — choose by the user's prompt (see `references/prompts.md`):

| Intent | Trigger examples | What you do |
|---|---|---|
| **A. Setup** | "Run HFCs" | Discover → 4 early gates (config reuse, data found, instructions, completion signal) → everything else decided silently → build → open the condensed report + the final Review & Approve gate (5th) → push to the tracking file |
| **B. Post-feedback** | "Process HFC feedback" | Clone → list Open+Comment rows → per row: read + write fix code → apply (single pass) → merge back → confirm → commit |

Authority (read; do not invent standards):

- `references/interaction.md` — **AskUserQuestion** UX (required for all gates; guess-then-correct, not typed mega-strings)
- `references/check_modules.md` — M1–M14 specs + the required-gate window + nested skip-logic
- `references/issue_tracking_schema.md` — the issue-tracking file's schema, including the `Status` lifecycle
- `references/role_map_schema.md` — every `role_map.yaml` field you determine yourself, what it means, and which handful `profile_roles()` still fills in on top
- `references/checklist.md` — package completeness
- `references/flags.md` — failure modes
- `references/prompts.md` — exact trigger phrases
- `references/ai_use.md` — no PII to commercial AI

Helpers (prefer `Rscript` rather than reimplementing):

- `scripts/profile_dataset.R` — lists every candidate file under the configured Input Data Directory (no classification — you decide which is the microdata/form/roster/context doc), then, once `role_map.yaml` names the microdata file, profiles every one of its columns (type, label, missingness, cardinality, sample values) for you to read and reason over
- `scripts/preview_modules.R` — write `hfc/config/modules.yaml`, a commented draft of proposed module defaults (run at the start of A2, applied silently unless the user asks for a Deep Review walkthrough) — requires `role_map.yaml` to already exist

- `scripts/rebuild_report.R` — post-resolution report refresh (Pipeline B step 7): re-runs checks against the latest data, drops Resolved/untracked findings from `<MMDD>_HFCs.html` and its `detailed/<MMDD>_HFCs_detailed.html` copy only (`issue_tracking.xlsx` keeps full history)
- `scripts/apply_feedback.R` — post-feedback CLI (`clone` / `list-open` / `apply` / `needs-review`); fix logic is agent-authored, see `scripts/lib/apply_feedback_helpers.R`
- `scripts/merge_issues.R` / `scripts/merge_resolutions.R` — fold a dated snapshot / resolutions clone back into `issue_tracking.xlsx`, producing a `merged_*.xlsx` for the agent to review
- `scripts/commit_merged_issue_tracking.R` — the only script that ever overwrites the live `issue_tracking.xlsx` (Tracking and Completion sheets together), run only after explicit AskUserQuestion confirmation
- `assets/summary_message_example.md` — annotated calibration example for the A4 long Summary narrative (detailed report)
- `assets/summary_condensed_example.md` — annotated calibration example for the A4 condensed message (the parent report, and the chat FYI)
- `assets/check_templates/` — M1–M14 real, runnable per-module scripts, copied into `hfc/code/checks/` at build time (same logic as `scripts/lib/run_checks.R`'s `check_mN()` functions, `scripts/lib/media.R` for M13); the Input Data Directory is read live from `config.json` each time a copied script runs, not frozen at generation time. `hfc/code/checks/main.R` (also copied every build) runs every one of these in one call — it sources each and calls the function it defines, never a second copy of their logic.
- `scripts/lib/media.R` — M13's check: flags only a media-indicating column (one you named in `role_map.yaml`'s `audio_file_cols`/`image_file_cols`) that's completely empty across every surveyed row, no on-disk file access
- `scripts/lib/geo_timezone.R` — country → IANA timezone lookup/resolver, given the country you determined in A1 (applied silently; only shown back to the user under a Deep Review walkthrough)
- `scripts/lib/form_logic.R` — SurveyCTO relevance / nested skip-logic helper + M4's group/section parsing
- `scripts/lib/product_structure.R` — write `hfc/structure.html`
- `scripts/lib/check_modules_preview.R` — write the commented `hfc/config/modules.yaml`
- `scripts/lib/module_desc.R` — per-module report descriptions computed from this project's actual configured thresholds
- `scripts/lib/pipeline_core.R` — shared "run checks + write `hfc/outputs/issues.csv`" step used by both `run_setup_build.R` and `rebuild_report.R`
- `scripts/lib/balance_tables.R` — M12 Balance Tables' four gt-rendered tables per configured grouping; shares completion/roster logic with M1 via `run_checks.R`'s `compute_completion_flag()`/`compute_replacement_roster_summary()`
- `scripts/lib/report_contract.R` — validates a built report's HTML against `assets/report_sections.json`; runs automatically (non-fatal) at the end of both `run_setup_build.R` and `rebuild_report.R`
- `scripts/lib/validate_config.R` — structural config validation: every field in `references/role_map_schema.md`'s agent-determined table must be present (even as `null`/empty when not applicable), `entity_id`/`data_file_path`/`timezone` must be genuinely resolved, plus missing columns, ungoverned gates, a `version_map` date gap, …; runs automatically at the start of both build scripts, `stop()`s with a collected, readable error list naming exactly what's missing
- `scripts/lib/verify_merge.R` — the 3-way merge check (dropped/unexpected `finding_id`, content diffs) run automatically inside `merge_issues.R`/`merge_resolutions.R`, before either ever writes a `merged_*.xlsx`
- `scripts/lib/issue_store.R` — `verify_tracking_integrity()` (row-count/blank/duplicate `finding_id` check, runs automatically before the live file is ever committed) and `patch_tracking_cells()` (the only safe way to hand-patch a few cells in the live tracking file — always read-modify-write through `read_named_tracking_file()`/`write_named_tracking_file()`, never a raw `openxlsx` call)

## Interactive confirms (AskUserQuestion) — guess first, correct if wrong

**Required.** Read and follow `references/interaction.md`.

The core pattern for every confirm in this skill: **the agent always states its own best guess first, in plain language, then gives the user a fast way to accept or correct it** — one atomic fact per tab, minimal text, packed into as few windows as possible. Two structural terms used throughout this doc:

- **Window** = one `AskUserQuestion` tool call.
- **Tab** = one `question` entry inside that call, covering exactly ONE fact/guess. A window can hold up to 4 tabs, all shown to the user together as a single interaction.

**Standard tab template — use this for every tab:**
> *[Guess + how it's used. ≤2 sentences, no em-dashes.]*
> Option 1: starts with "Looks good" (e.g. "Looks good!", "Looks good, continue!")
> Option 2: contextual to the tab's subject, not literally "Needs correction" (e.g. "The list needs edits", "A mapping is swapped", "The threshold is wrong") — "(I will type in Other)" unless a named 3rd/4th option already covers the correction path

Rules:

- One fact per tab. Never bundle multiple independent guesses (e.g. duration column + SD rule + work hours) into a single tab's text — that was the old design and it's been reverted.
- Sentence 1 leads with the concrete artifact (real path, real column name). Sentence 2 states only what's needed to judge the guess, plus any real downstream effect on other checks (e.g. "every other check runs on that subset only") — never leave a consequential effect implicit.
- Options aren't always the generic "Looks good!"/correction pair. When a rule has a natural partial-accept split, or an obvious alternate mode, enumerate those as real, named options (up to 4) instead of routing everything through free-text Other.
- List full item sets explicitly in a tab's own text (e.g. every variable name, not "and 5 more") — only the *options* array is capped at 4, the description text isn't.
- Timezones are always stated as abbreviation + city/country + UTC offset (e.g. "CAT (Blantyre, Malawi, UTC+2:00)"), never a bare IANA name.
- **Pack windows to capacity.** Backfill spare tab slots in an earlier window rather than opening a new one for 1-2 leftover facts — minimizing window count matters more than keeping tabs topically pure. Only a genuine data dependency (a tab whose content requires output that doesn't exist until a prior tab's answer is acted on) justifies a new window. See the Gate map in `references/interaction.md` for the current window-by-window packing.
- Fallback only if AskUserQuestion is unavailable: state the guesses as a numbered list in chat and ask the user to reply "looks good" or describe corrections — still not a typed mega-string like `M1=Y M2=N`.

## Operating principles

1. **Only 5 gates in Pipeline A: Config reuse, Data found, Instructions, Completion Signal (all A1), and Review & Approve (A4, final).** Everything else the agent decides is applied silently, with no `AskUserQuestion` and no chat narration — no phase between the 4 early gates and the final one waits for confirmation. What's silently decided still isn't final until the user approves at Review & Approve: the live `issue_tracking.xlsx` is never written before that.
2. Never mutate original microdata in the configured Input Data Directory — agent-authored fixes write to `<HFC Output Directory>/Updated Data/<stem>.<ext>` instead (one evolving file, never inside the git-tracked Code Output Directory).
3. **Guess first, correct if wrong** (see Interactive confirms above) — every gate that does fire states the agent's own best guess and gives one free-text correction option, never a long menu of choices. Applies to the 5 gates in principle 1, and to every tab in "Deep Review tabs" (A2) if the user asks for a walkthrough.
4. Feedback: **one shared file**, `issue_tracking.xlsx` — edited collaboratively by the agent, the RA, and the field team on the same file (Comment/Corrections/Status all live in the same Tracking sheet; no separate audit twin). OneDrive is **required** (no local fallback in the product — see A0): once `config.json`'s **HFC Output Directory** points at a folder the OneDrive desktop app is syncing, that folder is the **sole store** — every read/write is plain file I/O against it, and OneDrive's own sync client (not this skill) propagates changes to the cloud, so there is never a separate local-only copy. Two dated-snapshot subfolders live alongside it, inside the same synced folder: `intermediate/<YYYYMMDD>_issue_tracking.xlsx` (one per setup-build run) and `resolutions/<YYYYMMDD>_issues_resolution.xlsx` (the agent's working clone during a "Process HFC feedback" pass) — see `references/issue_tracking_schema.md`. A third subfolder, `Updated Data/<stem>.<ext>`, holds the agent-fixed copy of the survey microdata (see principle 2) — distinct from the dated snapshots above, it's one evolving file per source rather than one file per day. All four directories live in the skill's own `config.json` — the only file that matters, edited directly, no per-project override, no auth step or secrets in this package. The OneDrive folder is then shared manually (by whoever owns it) with collaborators via OneDrive's "Specific people" sharing UI.
5. Every build writes the report twice: `<MMDD>_HFCs.html` (the parent file, the **condensed** report: the agent-drafted `hfc/config/summary_condensed.md` followed by three trimmed sections the builder generates — Completion (overall, by enumerator, by date), Duplicates (only if any) and Form Version (the summary AND issues tables when form version issues exist, otherwise just "No form version issues found!"); Completion opens with a sentence stating Completion = completed surveys ÷ primary samples attempted — one page, header is just the title: no nav, About, or clickable section titles) and the full report as `detailed/<MMDD>_HFCs_detailed.html` (every section, plus the long narrative from `hfc/config/summary_message.md`), in both `hfc/outputs/` and the HFC Output Directory. **The top-left title of both pages is hardcoded `HFC MM/DD` (the generation day, same as the file name) by `report_title_label()` — never a project or brand name, never inferred, and never hand-edited into the HTML; if it looks wrong, rebuild.** Open only `<MMDD>_HFCs.html` (the condensed one) exactly once per pipeline pass, with `utils::browseURL()` (or OS `open`) — only after both messages (and, in Pipeline A, the README) are already folded in. Never at a preview/first build: opening an incomplete report and then silently rewriting the file underneath that open tab is confusing, not helpful.
6. **Must** write `hfc/config/modules.yaml` + `hfc/config/role_map.yaml` from the user's **confirmed** (guessed-then-corrected) options **before** calling the builder; also write `hfc/config/module_notes.yaml` whenever a custom check was confirmed, and `role_map.yaml`'s `important_vars` from the confirmed shortlist.
7. M9 (Field Request) has no built-in checks and defaults to **off / empty** — every M9 finding comes from a custom check the agent writes for this survey's specific content, driven entirely by what the user describes in the Instructions tab (A1, Setup window). A check tagging its rows `category = "field_request"` renders in M9's own Info-labeled section; every other custom-check category renders in the adjacent "Other" section instead.
8. **Specific-check requests are handled every run, from the Instructions tab (A1)** — there's no dedicated Field Request tab anymore. Read the Instructions answer for anything resembling a requested check every time; match it to a standard module first, else author an M9 custom check silently. Nothing said about checks → M9 stays off/empty, same effective default as before.
9. **No project README.** The skill writes only into `hfc/` (and the HFC Output Directory); it never generates a `README.md` in the Code Output Directory. `references/ai_use.md` still applies to how the user documents AI assistance.
10. **M13 media, redesigned:** the ONLY thing to flag is a media-indicating column that is completely empty across every surveyed row (a forgm/coding problem — the field isn't showing up in the enumerator's app, or the question is misconfigured) — never per-row file hygiene, and no on-disk file access at all. Which columns indicate media presence (audio/image filename columns, plus any qualitative open-text columns you identify) is decided silently in A1, from the column profile's sample values (a filename column's samples end in `.m4a`/`.jpg`/etc.) — only shown back to the user under a Deep Review walkthrough. Never put filename cols under M14.
11. **Completion is redefined:** it means whether all PLANNED surveys were conducted, not whether a started survey finished. The agent detects a completion signal — preferring a real gate/eligibility question read from the instrument, else a target/roster file, else a primary/secondary sample column — and confirms it via the Completion Signal gate (A1) — only when a signal is actually found; if none is found, M1 falls back to its original row-missingness heuristic and nothing else changes. Once confirmed, if a "gating" (or legacy "status") signal shows some rows were not completed, EVERY other check module (M2–M14) runs only on the completed/surveyed subset — incomplete rows are filtered out before any other check sees them. M1 itself always sees the full picture (the complete dataset, or the roster/target list). **Wherever a primary sample is known (a roster, or a primary/secondary column), completion is measured against it:** every Completion table reads Submitted | Submitted (Primary Sample) | Completed | Completion, with Completion = Completed (primary or replacement) ÷ Submitted (Primary Sample); without a primary sample the second column is dropped and Completion = Completed ÷ Submitted. Never assume what the roster doesn't say: no primary/replacement column, or IDs missing from the roster, are questions for the user (see A1 step 9d).
12. **Grouping defaults to Treatment/Control**, not geography — M1's completion-by-group stats table groups by a Treatment/Control column, identified by the agent's own judgment (A2 step 2), first. Geography is only used when no Treatment/Control column exists, or the user explicitly opts in to it alongside Treatment/Control (default: declined — ask about this only when a Treatment/Control column was actually found).
13. **Redundant/near-duplicate variables** (e.g. `treat` vs. `treat_ext`, `age` vs. `age_calc`): always silently keep the single most reasonable one in every shortlist you propose — never present both as if independently meaningful, and never ask the user to pick between them.
14. **Country inference must come from geography in the data** (district/region/village/site names, or a GPS bounding box), never from the input folder's name/basename — that's a report-title convenience only, not a location signal.
15. **Be careful about assent vs. consent** — they are different concepts (assent = the child/minor's own agreement; consent = the parent/guardian's, or an adult respondent's own). Decided silently in A1, from the column names/labels in the profile, naming which column maps to which concept — under Deep Review, its own tab, never bundled with anything else.
16. **Nested questions:** when form `relevant` says a child item is skipped, do not flag blanks as missing.
17. All product code/artifacts under **`hfc/`**.
18. **Report-wide sort:** every issues table sorts by date (most recent first), then enumerator, then unique ID — module sections stay in their fixed order (M1..M14), but there is no severity/worst-first ordering within a table. Dateless aggregate-level findings (group/enumerator-level, never tied to one day) sort last within their module. Every row-level finding matching the confirmed last date also appears in the dedicated Last Day tab (aggregate findings never can, since they have no date).
19. **Never ask a tab whose subject a prior answer already resolved.** Applies to the 4 early gates, and to a Deep Review walkthrough: check whether a topic is already settled — by A1's Instructions answer (free text or a hand-edited, non-blank value in `modules.yaml`/`role_map.yaml`) — before presenting it, even under "Walk me through all modules." If resolved, skip that tab and state the fact once in chat instead of re-asking. Concrete example: declining GPS checks entirely (`M10.on: no`) skips the Map focus tab too, since there's no map to focus without GPS data — `write_html_report()` ties the map's rendering to `M10.on`. (GPS Map itself never needs a threshold tab — it's a pure visualization by default, see Operating Principle 21.) If skipping drops a Deep Review window to ≤1 remaining tab, backfill into a neighboring window rather than firing a near-empty one for a single leftover fact.
20. **GPS Map (M10) never flags a point by default — visualization only.** Plots every submission with a valid coordinate; no distance threshold, no flagged points, no findings table, regardless of sector or project. Do not propose a distance-threshold tab as part of the standard setup flow. The old median-reference distance-outlier logic still exists, but only as an advanced opt-in (`modules$M10$advanced_distance_flag$on`) — surface it only if the user's own Instructions specifically ask for GPS-based flagging.
21. **Missingness (M7) is descriptive only by default — never flags an enumerator or a variable as an issue**, on either the question or the enumerator level; it's a reference table, not an issue list. The old enumerator-level flagging logic still exists as an advanced opt-in (`modules$M7$advanced_enum_flag$on`) — surface it only if the user's own Instructions specifically ask for missingness to be flagged, not just reported.

## Pipeline A — Setup

### A0. Config pre-flight (mandatory, every run)

There is no "survey project root" and no local-only mode — everything is driven by `skills/hfc-agent-skill/config.json`, naming four directories: **Input Data Directory**, **Media Folder Directory** (optional), **HFC Output Directory**, **Code Output Directory** (Input Data Directory, HFC Output Directory, Code Output Directory are required). Before proceeding to A0b/A1, verify `config.json` is fully configured — real paths, not the shipped `<...>` placeholders (this is exactly what `require_hfc_config_ready()` in `scripts/lib/issue_store.R` checks — every CLI script in this skill calls it automatically and `stop()`s with the same instructions below, naming the specific missing field, so this gate is also enforced in code, not just in this doc).

- **If it's already fully configured:** say so briefly in chat (name the three configured directories) and continue to A0b — no AskUserQuestion needed, there's no choice to make.
- **If any required field is missing or still a placeholder:** stop here. Tell the user, in this order: (1) run `Rscript <skill_dir>/install.R` if packages might be missing, (2) make sure the OneDrive desktop app is installed and signed in on this machine, and note the local folder it syncs to, (3) edit `<skill_dir>/config.json` — set Input Data Directory, HFC Output Directory, and Code Output Directory to real absolute paths (Media Folder Directory optional) — this is skill-level config, applies to every run using this skill copy. Do not proceed with Pipeline A or B until they confirm this is done and the pre-flight succeeds.

### A0b. Config-reuse gate (Window: Config reuse — conditional)

Immediately after the config pre-flight passes, check whether `hfc/config/role_map.yaml` **and** `hfc/config/modules.yaml` already exist under the configured Code Output Directory (a prior run). If neither exists, skip straight to A1 — nothing to reuse yet, no window shown. If they exist, one tab, three real options (no generic Other needed, these three cover it):

> *Found a saved setup from a prior run. Rebuild using it as-is?*
> - "Yes, reuse and rebuild (recommended)" — proceed straight to A4 build with the saved configs; skip A1 and A2 entirely (the existing reload logic in `run_setup_build.R` already handles this).
> - "No, start fresh" — delete `hfc/config/role_map.yaml` and `hfc/config/modules.yaml` (only those two files), then run A1–A4 normally as a first-ever setup.
> - "Let me edit the config files first" — state the paths (`hfc/config/role_map.yaml`, `hfc/config/modules.yaml`), wait for the user to confirm they're done, then proceed straight to A4 build; the existing reload logic picks up their hand-edited values automatically.

### A1. Discover, gather instructions, detect completion signal (Windows: Setup — 2 tabs, always [Gates 2-3]; Completion Signal — up to 1 tab, conditional [Gate 4])

**Only four gates fire during a normal setup run: Config reuse (A0b), Data found, Instructions (both below), and Completion Signal (end of this section).** Everything else this doc used to ask about — Entity, Country, Daily target, Replacement sample, and every module-confirmation window in A2 — is now decided **silently**: the agent applies its own best guess, writes it directly to `role_map.yaml`/`modules.yaml`, and moves on, with no `AskUserQuestion` call and no chat narration. The exact guess logic for each of those is unchanged from before — it's collected in **"Deep Review tabs"** at the end of A2, replayed only if the user asks to "Walk me through all modules" at A4's final Review & Approve gate.

**Reading order, once data is found but not yet deeply read: Instructions → project description (`context_doc`) → survey instrument/form → the microdata itself.** Each step below is informed by everything resolved before it, so the most inference-heavy step — loading and profiling the actual data — runs last and skips whatever's already known instead of duplicating it.

1. Run `scripts/profile_dataset.R` in the configured Input Data Directory only — no searching elsewhere, but including any nested subfolders. With no `data_file_path` in `role_map.yaml` yet, it lists every candidate file's path/extension/size/row-column count/sheet names, with **no classification at all** — you decide which one is the microdata, which (if any) is the survey instrument, which (if any) is a target/planned-sample roster, and which (if any) is a project-description/PAP document, by reading the actual candidates: a form's `.xlsx` has `survey`/`choices`/`settings` sheets; a roster looks like respondent IDs plus a target-vs-actual or primary/secondary-style column; a context doc's content (not just its filename) reads like a project description. Open anything ambiguous before deciding — never classify from the filename alone. Write your choices to `role_map.yaml`'s `data_file_path` (required), `form_file_path`, `roster_file_path`, `context_doc_path` (each optional — `null` if none exists).
   **Roster hunt — make an extra effort.** In an RCT the sample roster (the planned primary sample plus its replacements) is the most important file after the microdata: it drives completion, replacement tracking and most downstream checks. Before concluding there is none, open **every** candidate that isn't the microdata or the form — **all sheets** of every `.xlsx`, not just the first — and look for: respondent IDs that match the microdata's IDs, a column whose values separate primary from replacement/secondary respondents (read the values, don't trust the header), a replacement rank/queue column, strata columns (village, facility, arm), and filename hints (sample, roster, listing, frame, target, replacement, assignment). Check too whether the project document (PAP) mentions a sample list or replacement protocol. Never decide "no roster" from filenames alone, and never skip a file because of what its name contains.
2. **If nothing is found:** tell the user to drop files into the configured Input Data Directory, then try again. Do not proceed without data.
3. Form optional: proceed data-only; note M9 / M3 / nested logic weaker.
4. **Write a blank `hfc/config/modules.yaml`** immediately:
   ```bash
   Rscript .claude/skills/hfc-agent-skill/scripts/preview_modules.R --blank
   ```
   Writes a commented draft with every M1–M14 block present but unfilled (just its `desc:`/comment header) — no data dependency, safe to run before any role profiling. Its real path is stated in the Instructions tab below, inviting the user to pre-fill anything they already know (module on/off, thresholds, variable lists) directly in the file instead of waiting to be asked.
5. **Window "Setup" — 2 tabs, fires immediately, before any role profiling:**
   - **Data found** (Gate 2): sentence 1 states the real paths found (data file, form if any, and project description/PAP document if found); sentence 2 states row count, column count, and collection date range; **a third sentence always states the sample roster**: its path, row count and which column marks primary vs replacement, or, when none was found after the roster hunt, plainly "No sample roster found" together with a direct question — *is there a sample roster (primary + replacement list)? If so, drop it in the Input Data Directory and tell me.* If the user supplies one, re-run discovery and redo the roster hunt on it; if they confirm there is none, continue without.
   - **Instructions** (Gate 3): *"Any specific instructions for this data or this HFC check session? This can be anything I should know before diving in, e.g. disabling checks, naming the country, or specific checks you'd like run."* States the blank `modules.yaml`'s real path (from step 4) and invites pre-filling it directly, or leaving it for the agent to guide the rest of setup. Options: `"All good!"` / `Other`.
6. **Apply the Instructions answer before doing anything else:**
   - Interpret the free text as concrete facts/directives (e.g. "no GPS checks" → `M10.on: no`; a stated country → skip country inference and use it directly), and re-read `modules.yaml` for any hand-edited, non-blank values. Both become **already-resolved facts** — every silent decision from here on checks against them first instead of re-guessing (Operating Principle 19).
   - **Specific check requests:** match each one against the standard M1–M14 mechanics first (e.g. "flag surveys under 10 minutes" → set M4's threshold; "check for outliers on income" → add `income` to M6's variable list). Anything that doesn't map onto a standard check becomes an M9 Field Request custom check — design a check name, write `hfc/code/checks/<name>.R`, register it under M9/`custom`, and write its ≤3-sentence plain-English description to `hfc/config/module_notes.yaml` (`custom.<name>.label`/`.description`), same authoring mechanism as before, just triggered here and done silently (no separate confirm). A genuine field/daily-reconciliation check tags its rows `category = "field_request"` so it renders in M9's own Info-labeled table; any other custom category renders in the adjacent "Other" section instead. If Instructions says nothing about specific checks, M9 stays off/empty — same as the old "No additional checks" default, just without a dedicated tab asking about it.
7. **Now** read remaining context, in order, each informed by everything resolved in step 6:
   a. **`context_doc`, if found** — the Read tool handles PDF and text/markdown directly. If it's a `.docx`, run `Rscript <skill_dir>/scripts/lib/docx_text.R "<path>"` first (prints the path to a plain-text extraction, no new dependency — it's just an unzipped `word/document.xml`) and `Read` that instead of the binary file. Legacy binary `.doc` (pre-2007, not a zip container) can't be parsed this way — for that one format only, say so briefly in chat and ask the user to export it as `.docx` or PDF instead, and move on without blocking setup. Treat its contents as **background context only** — survey purpose, design, treatment arms, target sample/completion, key outcome variables, timeline. It is never itself a data source: never parse findings or role fields out of it mechanically, and never let it silently override what the actual microdata shows — if the two conflict, trust the data and flag the discrepancy in chat. If multiple candidate documents were found with no clear name match, don't guess — name them all in chat and ask which one, in the same message as the Instructions tab's summary (no separate tab).
   b. **The survey instrument/form, if found** — run `Rscript <skill_dir>/scripts/lib/form_text.R "<form_path>"` first (prints the path to a plain-text dump of **every sheet** in the workbook, not just the first) and `Read` that dump, never the raw `.xlsx` directly — a real SurveyCTO/XLSForm instrument routinely spreads what's needed across several sheets (`survey`: question name/type/label/relevant/required; `choices`: the value labels behind every `select_one`/`select_multiple` question, e.g. what code `1` vs `2` actually means; `settings`: form title/id/version), and reading only the first sheet would silently miss the `choices`/`settings` content entirely. Covers skip-logic (`relevant`), question structure, and choice-code meanings; informs M9/M3/nested-logic judgment as well as gate-pass-value and sentinel-code interpretation.
   c. **The microdata itself, loaded and profiled last.** Run `scripts/profile_dataset.R` again — now that `role_map.yaml` has a `data_file_path`, it profiles every column (type, label, % missing, distinct count, a handful of sample values) instead of listing files. Read this like an analyst reading a data dictionary, not a script matching column names against a pattern list — a `.dta`/labelled `.xlsx`'s variable labels are often more informative than the raw column name. Every field below is decided **silently** (write it directly to `role_map.yaml` — see `references/role_map_schema.md` for the full list and format of each — no confirmation, no chat narration; see Deep Review at the end of A2 to replay any of it on request), lightened or skipped wherever step 6 already resolved it:
      - **Entity ID** (`entity_id`): which column identifies each respondent/case/household — usually near-100%-unique, named or labelled like an identifier, and not a measurement column (duration, GPS, a score, an age).
      - **Entity Label** (`entity_label`): a Title-Case guess for what to call the entity (e.g. "Household" for a column named `hhld_id`) — used everywhere the entity is displayed: the HTML report's findings tables *and* the xlsx/csv issue-tracking export.
      - **Group, Enumerator, Start/End/Duration, GPS x/y, Age, Assent/Consent** (`group`, `enum`, `start`, `end`, `duration`, `x`, `y`, `age`, `assent`, `consent`) and each one's own human-readable **name field**, if the data captures one separately from its ID (`group_name`, `enum_name`, `entity_name_field`): read the column names/labels/sample values and decide which column plays which structural role — `null` for any role this survey genuinely doesn't have (e.g. no GPS captured). Assent and consent are different concepts — get the naming direction right (assent = the minor's own agreement; consent = the guardian's/adult's).
      - **Media-indicating columns** (`audio_file_cols`, `image_file_cols`, `consent_image`, `assent_image`, `audio_flag`): a character column whose sample values end in an audio (`.m4a`/`.mp3`/…) or image (`.jpg`/`.png`/…) extension is a media filename column; among the image columns, which one is the signed-consent photo vs. the child-assent photo (if any); a separate audio-consent flag column, distinct from an audio filename column, if one exists. Plus any qualitative/open-text columns you identify as capturing qualitative data.
      - **Duplicate-check key extras** (`dup_key_extra`): only relevant if Entity ID isn't already 100% unique on its own (a respondent legitimately repeats across rounds) — round/wave/phase-like columns that disambiguate it.
      - **Form-version column** (`form_version_col`): a column recording which version of the instrument a submission used, if the form changed over the collection window.
      - **Section-level timing pairs** (`section_time_pairs`): matching `<section>_start`/`<section>_end` (or `start_<section>`/`end_<section>`) column pairs, if the form times individual sections separately from the overall interview.
      - **De-identification defaults (fixed, never guessed or asked):** HFC data is de-identified by default — the entity's real name is never available, but enumerator names usually are. Set `role_map.yaml`'s `entity_display = "id"` (Entity always shows the raw ID), `enumerator_display = "name"` and `group_display = "name"` (Enumerator/Group show the name when one exists, else the ID) — applied everywhere (HTML report findings tables *and* their descriptive stats tables, `issue_tracking.xlsx`/`issues.csv`) via `resolve_display_vec()` (`scripts/lib/utils.R`). Only change one if a user **explicitly** asks (e.g. "this data isn't anonymized, show respondent names" or "show enumerator IDs instead"): edit the matching field directly in `hfc/config/role_map.yaml` and rebuild — never guess or proactively offer this.
8. **Country**: skip entirely if step 6 already stated it. Otherwise, look at the same column profile from step 7c: if an explicit country-name/code column exists, use its values directly. If not, read district/region/village/site-name-like columns' sample values (plus GPS coordinates, if captured, as a bounding-box sanity check) and use your own general-knowledge judgment to state a best-guess country — **never infer this from the input folder's name/basename**, that's a report-title convenience only. Resolve the guessed country's timezone via `resolve_country_timezone()` (`scripts/lib/geo_timezone.R`) — timezones are always abbreviation + city/country + UTC offset (e.g. "CAT (Blantyre, Malawi, UTC+2:00)"), never a bare IANA name. Apply silently — write `country`/`country_col`/`timezone` directly to `role_map.yaml`, no confirmation. `timezone` (or, in multi-country mode, a `country_timezone_map` covering every country value present) is required — the build stops rather than silently defaulting to the machine's own local timezone.
9. **Detect the completion signal.** Gating (a real screening/eligibility question from the instrument) is the primary, preferred signal. Detection order:
   a. **gating (preferred)** — read the instrument's `type`/`label`/`relevant` columns like an analyst would, looking for root-level screening questions whose failure skips most/all of the rest of the survey (household presence, consent, age/eligibility checks). As a supporting signal, not a replacement for judgment, compute `gate_fanout_counts(form_map)` (`scripts/lib/form_logic.R`) — how many other questions' `relevant` expressions name each column as a parent, via the existing `relevant_parents()`; a high count is a strong hint of a true gate. Order confirmed gates by where they appear in the form (earliest first — later gates are only reached if earlier ones pass).
      **Non-completion reason, per failing value, not just per gate.** For each confirmed gate, read that question's own label and (for `select_one`) its full choice list from the same `form_text.R` dump. For every value that would count as a *fail* on that gate, write a short, specific reason phrase describing the substantive condition, not the gate's name and not the raw answer text — e.g. `hh_present` failing `"No"` → `"Household absent"`, `consent` failing `"No"` → `"Declined consent"`; a multi-choice ineligibility question gets one distinct phrase per failing value, never one generic phrase for all of them. Write this to `modules.yaml`'s `M1.gate_fail_reasons: {<gate_col>: {<failing_value>: "<reason phrase>", ...}, ...}` — additive alongside `gate_labels`, which stays as the fallback for any failing value with no specific entry (an unanticipated raw value, or an older config predating this field).
   b. **roster** — the file you named as `roster_file_path` in step 1, if any. Only relevant when no credible gate was found. When roster wins, completion-by-strata (village, health facility, Treatment/Control, etc.) reports the roster's own **target sample size** as the denominator — percent of the planned sample actually surveyed, not percent of submitted rows — so also check whether `modules$M1$group_vars` (the strata column(s) already detected in the survey data) exist by the same name in the roster file. If a strata column's name differs there (e.g. survey data has `village`, the roster has `village_name`), resolve the match by column-name similarity or by comparing raw values, and state it in the Completion Signal tab below — silent when the names already match (the common case).
   c. **primary_secondary** — a column within the surveyed data marking each row Primary or Secondary sample (no separate roster). Only relevant when no credible gate was found.
   If no gate, roster, or primary/secondary signal is found at all, there's nothing to confirm — skip the Completion Signal window entirely, and M1 falls back to its original row-missingness heuristic.
   d. **Replacement-sample structure — independent of a/b/c above, checked whenever a roster file exists at all** (even alongside a `gating` signal): inspect the roster's own columns for a Primary/Secondary-or-Replacement status column, a numeric position-in-the-replacement-queue column (only meaningful on non-primary rows), and a group column (e.g. health facility or village — matched by raw value against `roles$group` in the survey data). This is agent judgment, the same posture as reading the instrument for gates in step 9a — read the actual column names/values, don't guess from a fixed name list. The **status column alone** (read from the roster's own values: which column separates primary from replacement/secondary, and which values mean primary) is enough to measure completion against the primary sample; rank and group are only needed for the BY REPLACEMENT table and its queue-validity check. **If no column on the roster looks like it, do NOT guess or assume everything is primary — ask the user** (`AskUserQuestion`, in the Completion Signal tab): name the best candidate column(s) with the values you'd treat as primary, or offer "No such column: every roster respondent is primary (no replacements)" (plus the automatic Other). Save the answer: `modules.yaml` `M1.replacement_status_col` + `M1.replacement_primary_values`, or `M1.roster_all_primary: true` (only on the user's say-so). The build stops with a `NEEDS_USER_INPUT:` error while a loaded roster has neither (this also catches older saved configs).
      **Respondents not on the roster.** If the build stops with a `NEEDS_USER_INPUT:` error saying submitted IDs are not on the roster, ask the user (`AskUserQuestion`): the roster is the wrong file or its ID column is wrong (fix `roster_file_path` / `completion_roster_key_col`, rebuild), count them as non-primary extras (`M1.offroster_handling: non_primary`; they stay in Submitted and Completed, not in the primary denominator), or exclude them from the completion tables (`M1.offroster_handling: exclude`). Once chosen, later builds apply it silently and print an `Off-roster respondents:` line.
      **Non-start reasons.** When that same status column carries disposition values beyond simple Primary/Replacement (e.g. "Rejected," "Unavailable," "Rescheduled"), map each one onto `Rejected`/`Unavailable`/`Rescheduled`/`Other` and write the column name to `modules.yaml`'s `M1.nonstart_status_col` and the mapping to `M1.nonstart_reason_map`. This covers respondents never reached at all (no row in the survey data whatsoever) — their non-completion reason otherwise has nothing to derive from. Skipped silently, no fields written, whenever no such status column exists.
10. **Window "Completion Signal" — up to 1 tab, fires right after step 9, whenever any signal (gating, roster, or primary_secondary) was detected — Gate 4:**
    - If gating: states the guessed gate question(s) in form order with their labels (e.g. `hh_present` "Household present?", `consent` "Consents to interview?"), that the first failed gate wins (since later gates were never reached), and a sample of the derived `gate_fail_reasons` mapping so it's a fast eyeball-check, not a wall of JSON (e.g. "`hh_present`: No → 'Household absent'; `consent`: No → 'Declined consent'"). If a gate was clearly added to the form partway through data collection (e.g. it's absent from earlier submissions entirely), state the guessed `gate_min_date` exempting submissions before then from failing it. If one gate can legitimately be revisited after an earlier one misfires (typically consent), state it as the guessed `governing_gate`.
    - If roster/primary_secondary (no gate): state that signal instead (name the file/column, the downstream filtering effect) — when roster wins and step 9b needed to resolve a strata-column name mismatch, also state that mapping (e.g. "the roster's `village_name` column matches the survey data's `village`").
    - If more than one signal type is genuinely available at once, do NOT silently pick — name the conflict explicitly and flag it as needing a closer look.
    - Options: `"Looks good!"` / `"The list needs edits (I will type in Other)"`.
    - Skipped entirely (no tab) only when no signal at all was found.
    - **Daily target** and **Replacement sample** (guessed alongside the signal above): decided silently, same guess logic as before (daily target: the overall median enumerator-day submission count, as a starting proposal; replacement sample: the roster's status/rank/group columns, when step 9d found them) — written directly to `modules.yaml`'s `M1` block, no confirmation.
11. Persist everything (confirmed via the tabs above, or decided silently) to `hfc/config/role_map.yaml` — every field named in steps 1 and 7c-10 above, per `references/role_map_schema.md`'s complete list and format, plus: `completion_primary_signal` (now typically `"gating"`), `completion_roster_candidate`, `completion_roster_key_col`, `completion_roster_group_map` (only the entries step 9b actually needed to resolve — blank/omitted whenever strata column names already match), `completion_primary_secondary_col`, `completion_primary_value`. Do not write `completion_status_col`/`completion_status_complete_values` fresh — those fields are superseded by gating, kept readable only for backward compatibility with a config from before this change. `scripts/lib/validate_config.R` stops the build naming any required field you left out. Write to `hfc/config/modules.yaml`'s `M1` block: `completion_signal`, `gate_cols` (ordered), `gate_pass_values`, `gate_labels`, `gate_fail_reasons`, `gate_min_date`, `governing_gate`, `daily_target_per_enum`, `replacement_status_col`, `replacement_primary_values`, `replacement_rank_col`, `replacement_group_col`, `nonstart_status_col`, `nonstart_reason_map`.

### A2. Module configuration (fully silent by default — no windows fire here on a normal run)

1. Read `references/check_modules.md` and `references/interaction.md`.
2. Profile columns (names/types/labels only — no PII row dumps) and compute proposed defaults for every module (`default_modules()`), now using the roles confirmed in A1. **Identify the Treatment/Control column yourself**, from real column names and value distributions (e.g. `arm`/`condition`/`assignment`-like columns with 2-3 distinct values reading as Treatment/Control/T/C/1/0) — naming conventions vary too much by sector to pattern-match reliably, so read the actual data rather than trusting a fixed name list. Apply silently — write `role_map.yaml`'s `treatment_control_col` directly, alongside a short human label for it (`treatment_control_label` — e.g. "Treatment Arm," "Extension Arm," "Study Arm," whatever this project's own instrument/context_doc actually calls it; "Treatment Arm" is the fallback when nothing more specific is evident) — used by Survey Duration's own ISSUES table (report_sections.json), the one table on the page that always shows this column regardless of `roles$group`. Both persisted in step 7 below. Fall back to geography only when no Treatment/Control column exists.
3. **Write the informed module config:**
   ```bash
   Rscript .claude/skills/hfc-agent-skill/scripts/preview_modules.R
   ```
   Merges fresh, role-informed guesses (on/off, thresholds, variables) with whatever's already sitting in `hfc/config/modules.yaml` from A1's blank draft (step 4) — any field the user hand-filled there wins; everything else gets a real guess (`merge_prefilled_modules()`, `scripts/lib/check_modules_preview.R`). Rewrites the same file in place, one module per commented block — a real file on disk the user can hand-edit at any time. This IS the file that ends up governing the actual build; corrections (from a "Walk me through all modules" pass, or a hand-edit the user mentions at the final gate) just edit this same file in place.
4. **Important variables shortlist (unified for M6/M8/M11/M7) — mandatory, every run:** propose up to 10 variables using your own judgment about what's contextually important to this survey — read column names/labels/content, informed by (not limited to) the profile's numeric/ordinal candidate pools, not driven by numeric-ness alone. When two or more candidates are near-duplicates of each other (e.g. `treat` vs. `treat_ext`), silently keep only the single most reasonable one — never present both. **Scan these variables' value distributions yourself for likely sentinel/missing codes** (99, -99, -9999, … appearing disproportionately outside the variable's normal range). When the form is available, cross-check each candidate against its question text/choice labels (`form_text.R`'s dump) rather than relying on the value pattern alone — a code the form's own choice list defines (e.g. "999 = Don't know") is a confirmed sentinel, not just a guess.
   Additionally, for M7 Missingness specifically, read through the full column list and select ~20 more variables (any type, not just numeric) you judge important for missingness reporting — broader than the unified shortlist above. Agent judgment only, write directly to `hfc/config/role_map.yaml`'s `missingness_extra_vars`. An RA who disagrees with the picks edits that file directly.
   **Ordinal/Likert variables** (`role_map.yaml`'s `ordinal_vars`) — among the important variables just shortlisted (and any other column worth a look), which ones are ordinal/Likert-shaped (a handful of ordered values)? Feeds M8's straightlining check directly; M8 turns off if this list is empty.
   **Never select a skip-logic-dependent (conditional) variable for the missingness pool by default** — check the parsed form's `relevant` column (`parse_form_relevance()`, `scripts/lib/form_logic.R`) for every candidate; if it has a non-blank `relevant` (it's a child of some other question), it's inherently conditional and gets excluded from both the unified shortlist and the M7 extra-vars list, even though `filter_expected_skips()` would correctly zero out the row-level denominator anyway — the point is not to propose it as a missingness check target at all. The only exception: the user explicitly asked to include that specific variable (Instructions tab) — then include it and don't second-guess the request.
5. **Decide every one of the following silently — write directly to `modules.yaml`/`role_map.yaml`, no `AskUserQuestion`, no chat narration:** form-version date-range mapping (only if `form_version_col` is set and 2+ versions detected); work hours window + weekend flag; last date of data collection; map focus; geography opt-in (declined by default whenever a Treatment/Control column exists); group label; Balance Tables groupings (declined by default unless the project genuinely looks like a randomized/multi-arm design). Entity/Group/Enumerator/timing/GPS/media/consent/assent/duplicate-key columns were already determined in A1 step 7c — this step wires them into `modules.yaml`, it doesn't redetermine them. Excel columns are always the standard `issue_tracking.xlsx` schema — never varies, see `references/issue_tracking_schema.md`. **The exact thresholds and tab wording for every one of these lives in "Deep Review tabs" below** — replayed only if the user asks to "Walk me through all modules" at A4's final Review & Approve gate.
6. **Generate clean variable labels (`var_labels`) — mandatory, every run, agent judgment only, no `AskUserQuestion` confirmation** (same posture as step 4's M7 extra-vars pick): by this point every column that can actually surface in a finding or the tracking sheet is known — the unified important-variables shortlist + M7's extra missingness vars (step 4), the media columns, the assent/consent/audio columns, and the duplicate-key/form-version columns (all decided in step 5). For each, read the raw column name and its instrument question label (already available from `form_text.R`'s dump, A1 step 7b) and write a short, clean, human-readable label — neither the bare column name nor the verbatim question text (e.g. `q14_wait_time_min` + "How long did you wait to be seen, in minutes" → "Wait time (min)"). Write directly to `hfc/config/role_map.yaml`'s `var_labels: {colname: "Clean Label", ...}`. Falls back to the raw column name wherever a column has no entry (e.g. a rebuild against an older config) — never blocks a build. An RA who disagrees with a label edits the file directly, same as `missingness_extra_vars`.
7. Write every module setting decided above (silently, or via a Deep Review correction) into `hfc/config/modules.yaml` in place (its comments and every other module's settings stay untouched), then write the remaining `hfc/config/role_map.yaml` fields: `important_vars`, `missingness_extra_vars`, `var_labels`, `last_date`, `treatment_control_col`, `treatment_control_label`, `geo_group_col`, `geo_group_opted_in`, `map_focus`, `group_label`.

### Deep Review tabs (only if the user asks to "Walk me through all modules" — A4's final Review & Approve gate)

The report, `hfc/structure.html`, and the pending tracking snapshot have already been built once, silently, using every guess below. When the user asks for a walkthrough instead of approving, replay these windows in order — each tab pre-filled with the value already computed, so it's a fast confirm-or-correct pass, not starting over — apply any corrections directly to `modules.yaml`/`role_map.yaml`, rebuild, and re-ask the final gate.

**Window "Entity & Country" — up to 2 tabs, one atomic fact each, standard template:**
- **Entity**: "The entity here is `<Label>`, in place of `<column>`. I'll use this name across the report and tracking sheet."
- **Country**: "Data collection country is `<Country>`. Timezone is `<abbrev>` (`<city, country>`, UTC`<offset>`)."

**Completion Signal window, extra tabs (alongside the signal tab from A1 step 10):**
- **Daily target**: guesses a starting number (the overall median enumerator-day submission count across the whole dataset, as a reasonable proposal) and asks the user to confirm or state their real per-enumerator daily target. Options: `"Looks good!"` (accept the guessed number) / `"No daily target, skip this check"` / `Other` (type in the real number).
- **Replacement sample** (only when A1 step 9d found status/rank/group columns): states the guessed status column + which values mean Primary, the rank column, and the group-matching column — e.g. *"In the roster, `status` marks Primary/Replacement and `rank` gives each replacement's position, grouped by `facility_id`. I'll report what share of each group's targeted sample was replaced, and flag any group where a replacement completed without earlier-ranked replacements having been attempted first."* Options: `"Looks good!"` / `"The columns need edits (I will type in Other)"`.

**Window "Keys & Hours" — up to 4 tabs:**
- **Duplicate key**: restate the determined key.
- **Form version** (only if 2+ versions detected): guessed version column + date-range↔version mapping. With no confirmed windows, M3 falls back to each day's most-used version as the expected one (Expected Dates and mismatch findings both derive from it).
- **Duration column** (M4): the guessed column — duration-field naming varies a lot across form platforms (SurveyCTO/ODK/Kobo/CommCare), so this is worth a real look if reviewing. Its 3 SD outlier threshold is a fully fixed default, never mentioned here. **One-sided by default: only `short_duration` flags fire** — a long interview isn't inherently a data-quality problem, so `long_duration` flagging stays off unless `modules$M4$advanced_long_flag$on` is explicitly turned on (surface it only if the Instructions answer specifically asks for long-duration flagging). When `roles$section_time_pairs` also found section-level start/end timestamps (e.g. `introduction_start`/`introduction_end`, `training_start`/`training_end`), extend this same tab's options with a real named choice: "Looks good!" (overall duration only, default) / "Also check timing by section: `<Section1>, <Section2>, ...`" / `Other`. If chosen, persist the selected pairs to `modules.yaml`'s `M4.section_pairs` — each opted-in section then gets its own SD-outlier flagging (`short_duration`, same fixed 3 SD threshold, plus `long_duration` too if the advanced flag is on) alongside the overall duration check, not instead of it.
- **Work hours** (M5): the guessed work-hours window + weekend flag, as one rule — offer real partial-accept options, not just Looks good!/Other: "Looks good!" (flag both) / "Flag work-hours only" / "Flag weekend only".

**Window "Dates, Variables & GPS" — up to 4 tabs:**
- **Last date**: the detected max date, states it drives the Last Day tab. Options: "Looks good!" / "Include more days (I will specify)".
- **Variables**: the full important-variables list, spelled out by name (not truncated). If the Instructions answer named specific fixed numeric bounds for one or more of them, set `modules$M6$outlier_mode: "fixed"` and the named `fixed_thresholds` here instead of the SD rule.
- **Sentinel codes**: the six default NA codes (-99, -999, -9999, 999, 9999, 99999) already apply to every numeric statistic (never flagged as outliers); this proposes only ADDITIONAL codes found in the data (e.g. 888, 99), which are added to the defaults (written to `M7.sentinel_codes`).
- **GPS coordinates** (M10): restate the detected latitude/longitude columns, only when GPS data was found. **No distance-threshold tab** — GPS Map never flags a point by default (Operating Principle 20); only mention the advanced opt-in flag if the Instructions answer specifically asked for GPS-based flagging.

**Window "Media, Map & Grouping" — up to 4 tabs:**
- **Media columns** (M13): restate the media-indicating columns.
- **Map focus**: the default (Country). Conditional: only when GPS data exists and M10 is on.
- **Add geography?** (only if a Treatment/Control column was found): real Yes/No options, not Other — "No, Treatment/Control only (recommended)" / "Yes, add geography too".
- **Group label**: the guessed label for what `roles$group` (e.g. `school_id`) should be called throughout the report/tracking sheet (e.g. `school_id` → "School", `village` → "Village").

**Window "Wrap-up" — up to 3 tabs:**
- **Consent mapping** — its own tab, never bundled with anything else: state which column maps to assent, consent, and audio-consent, explicitly naming each. Assent and consent are different concepts (minor's own agreement vs. guardian/adult consent); get this right.
- **Balance Tables groupings** (M12): conditional — only offered when a Treatment/Control-like column exists AND the project genuinely looks like a randomized/multi-arm design (most projects aren't; declined by default, no tab at all when it doesn't apply). States the guessed grouping column(s) and a starting covariate shortlist (reusing the important-variables list); confirmed groupings are written to `modules.yaml`'s `M12.groupings`.
- **Excel columns**: the standard `issue_tracking.xlsx` schema (`Status` Open default; any Open row with a non-empty Comment is eligible for the agent to interpret and resolve in Pipeline B — Accepted/Revise are advisory triage values the field/RA can still set, not a hard gate; Resolved/Needs Review are set by the agent, always in the resolutions clone first, never written straight to the live file — see `references/issue_tracking_schema.md`). "Looks good!" / "Modify columns (I will type in Other)".

(Field Request/additional checks isn't part of Deep Review — it's handled once, at A1's Instructions tab, every run, regardless of `review_mode`.)

### A4. Build

Length follows however many real, distinct points the latest day actually produces — don't pad, but don't compress real points just to keep it short.
   **List format: bullets (`-`) by default, numbered (`1.`, `2.`, ...) reserved for lists of issues.** The enumerator roster (2f) and the reasons-for-non-completion breakdown (2b), when it earns its own list, are both status/data content, not issues — always bullets. The day every figure refers to is the **last day of data collection** (`roles$last_date`, not the day the report is generated), written as abbreviated month + zero-padded day, e.g. `Aug 17`, `May 09` — the same string in every sentence, including `synced through <Mon DD>`, `N submissions on <Mon DD>`, `The N non-completions on <Mon DD>` and `Enumerators on <Mon DD>:`. `format_summary_date(roles$last_date)` (`scripts/lib/build_outputs.R`) gives the exact string; the builder warns when a message uses a relative or numeric date or never names that day.

Every sentence describes the actual data-collection reality on the last day (completion, issues, durations, enumerators) — nothing about the software that produced the report. **Field Request (M9) entries are never narrated in this long narrative either (the condensed message may highlight them)** — they're the field team's own status reconciliation, not a data-quality issue, regardless of how much activity happened there that day; only real findings/issues belong in this message.

Spacing follows the same logic — a paragraph of lead sentences, then each list on its own lines, not one dense block.
      a. **The one cumulative topic.** The latest day's own attempted/completed/non-completed counts (M1's `stats$by_date`), alongside cumulative completion **measured against the primary sample whenever one is known** (see A1), written as **the same four-sentence opening in BOTH messages** (read the numbers from the build log's `Primary sample:` line and M1's tables): (1) `Hi @team, HFC update for <project name>, synced through <Mon DD>.` (the long narrative may say what the update covers instead of the project name) (2) `There were <N> submissions on <Mon DD> from <N> distinct <entities, plural>, <M> completed.` (entity noun from `roles$entity_label`, pluralised, singular when 1) (3) `Cumulative: <X> surveys completed (<P> primary, <R> replacements) against <T> primary-sample <entities> scheduled.` (4) `<A> primary samples attempted (submitted), that is <Z>% completion so far!` Model: "Hi @team, HFC update for the Uganda AI Extension Services pilot (Mubende), synced through Aug 17. Completion is Completed ÷ Submitted (Primary Sample), so it can pass 100% when replacements completed for primaries that never submitted. Variants: no replacements completed -> drop the parenthetical; primary known but no planned target (primary/secondary column) -> drop "against ... scheduled"; no primary sample at all -> `Cumulative: <X> surveys completed out of <M> submitted, that is <Z>% completion so far!`. Then completion % by group, defaulting to Treatment/Control when that grouping exists.
      b. **Reasons for non-completion** among that day's non-completions specifically, when the confirmed signal is `gating` and `stats$by_reason` has any real entries for the day — state the breakdown by name and count (e.g. "3 refused, 2 absent, 1 ineligible"). One or two reasons can fold into 2a's sentence; three or more render as their own short bullet list instead (never numbered — these are reasons, not an issues list).
      c. **Outliers worth a second look** (M6 only), from that day's submissions only — narrate a genuine flag in plain language with its actual value, and when you don't have enough local-context judgment to be sure it's wrong, pose it as a plausibility question rather than a flat assertion, same as a field RA would.
      d. **That day's own survey duration** (M4) — mean and median in minutes, from the already-computed "Survey duration on this day" block (Last Day tab), not the overall/cumulative duration stats. **Call this a survey duration issue, never an "outlier"** — "outlier"/"outliers" is 2c's word for M6 findings only; a long/short duration flag is a different check with its own vocabulary, even though both use a statistical threshold internally.
      e. **That day's own duplicates** (M2) by name, with the real `issue_tracking.xlsx` path and an `@mention`-style placeholder for follow-up.
      f. **Enumerator roster for the latest day** — every active enumerator's attempted-vs-completed tally for that day (compute fresh from the completed dataset or `hfc/outputs/issues.csv`, grouped by enumerator and the latest date — there is no dedicated pre-built stats table for this), plus an explicit, actionable call-out (named directly, with their last-active date and a concrete ask — e.g. an upload-by deadline) for anyone with zero submissions that day. Not just a below-target flag: the full roster, so the reader sees who did what, not only who's in trouble. **Always its own itemized bullet list** (one line per enumerator: name, attempted, completed) — never folded into a single prose sentence, regardless of how few enumerators worked that day, and never numbered — this is a roster, not a list of issues.
   3. **"Other issues:" numbered list, after the lead — the one place in this message enumerate is used, because it's literally a list of issues.** That day's own remaining row-level findings (M5, M8's per-day by-enumerator and within-submission checks, M3, etc. — M10 GPS Map and M7 Missingness are descriptive-only by default and won't normally contribute anything here, unless the project has their advanced opt-in flags on), plus any dateless/structural finding (M13/M14 column-empty) that's genuinely NEW since the previous report — check `issue_tracking.xlsx`'s Status and the most recently dated `<MMDD>_HFCs.html` already in `hfc/outputs/` (if any) to tell "new" from "already known." Translate a dataset-level finding (e.g. M13's "this column is empty") into entity/group-level specifics where possible ("were not available in N schools — schools X, Y, Z"), not merely restating the raw one-line finding. Never includes Field Request (M9) entries — those are excluded from the Summary entirely, not just from this list.
      **When a sentence reports a count or status that changed since a prior report, keep it self-contained — a reader who hasn't seen that prior report must still follow it.** (1) Say what the finding *means* before or alongside the number — don't assume the reader already knows what e.g. a "replacement-sequence gap" is. (2) Lead with the **current total**, stated plainly. (3) Treat "new since last time" / "resolved since last time" as a clearly-labeled aside, never as the sentence's only handle on the number — no bare "now", no bare "new:", no bare "gap has closed" without saying what closed. For example:
      - **Not this** (assumes the reader already knows the backstory): "Replacement-sequence gaps, now in 12 farmer groups (2 new: Kazilangoma Coffee Farmers Group, Kizige Coffee Farmers Group; Kyakadali Abamwe Farmer's Group's gap has closed): a lower-ranked replacement completed before an earlier-ranked one was attempted."
      - **This** (explains the concept, leads with the total, labels the deltas): "Replacement-sequence gaps — a lower-ranked replacement was interviewed before an earlier-ranked one was even attempted — currently affect 12 farmer groups, including 2 new on Aug 17: Kazilangoma Coffee Farmers Group and Kizige Coffee Farmers Group. (Kyakadali Abamwe Farmer's Group, flagged before, no longer has this issue.)"
      Write this as a real numbered list (`1.`, `2.`, ...) — `render_summary_narrative()` (`build_outputs.R`) turns numbered lines into a real `<ol>`, not literal digits in a wall of text. One item per theme, same "name real entities/counts" rule as the lead. Never fabricate detail the pipeline's own findings/data don't support (e.g. photo content) — no check module inspects media content, only whether a media column is entirely empty (M13).
   4. **One closing reminder line — only if something genuinely still open predates the last day.** Using the same Status/prior-report check as step 3, if anything not already covered above is still Open from an earlier day (or a longstanding structural issue already known before this report), add exactly ONE line stating the count and pointing at `issue_tracking.xlsx` (e.g. "There are also 4 issues from previous days still open in issue_tracking.xlsx — worth a review when you get a chance."). Never restate each one's own detail — steps 2-3 are for what's new/from the last day; this is a pointer, not a repeat. Omit this line entirely when nothing genuinely predates the last day.
   Write it to `hfc/config/summary_message.md` (plain text, overwritten each time — not `module_notes.yaml`); it appears only in the detailed report.
   **Condensed message** — write to `hfc/config/summary_condensed.md` (see `assets/summary_condensed_example.md`). This message is the top of the parent report (the builder adds the Completion, Duplicates and Form Version tables beneath it automatically) and **the message you post in chat as the FYI** (post this one, not the long narrative). Latest day only, with completion the one cumulative figure. Four spaced blocks, nothing else (the tables under it are generated, never written by you):
   1. **Opening paragraph:** **the same four-sentence opening in BOTH messages** (read the numbers from the build log's `Primary sample:` line and M1's tables): (1) `Hi @team, HFC update for <project name>, synced through <Mon DD>.` (the long narrative may say what the update covers instead of the project name) (2) `There were <N> submissions on <Mon DD> from <N> distinct <entities, plural>, <M> completed.` (entity noun from `roles$entity_label`, pluralised, singular when 1) (3) `Cumulative: <X> surveys completed (<P> primary, <R> replacements) against <T> primary-sample <entities> scheduled.` (4) `<A> primary samples attempted (submitted), that is <Z>% completion so far!` Model: "Hi @team, HFC update for the Uganda AI Extension Services pilot (Mubende), synced through Aug 17.    2. **Non-completions paragraph:** that day's non-completions, who, and each one's specific reason (`gate_fail_reasons`). Omit the paragraph when there were none.

## Pipeline B — Post-feedback

There is no built-in fix-classification engine. **You (the agent) read and interpret each eligible row yourself and write the fix code** — same philosophy as M9 custom checks: no fixed catalog of fix types, decide per row. Trigger: any row with `Status == Open` **and** a non-empty Comment is eligible — there is no separate Accepted gate. Everything in this pipeline operates on today's `resolutions/<date>_issues_resolution.xlsx` clone, never on `issue_tracking.xlsx` directly — the live shared file is only ever updated by the explicit merge-and-commit step at the end.

1. Create (or reuse) today's resolutions clone:
   ```bash
   Rscript .claude/skills/hfc-agent-skill/scripts/apply_feedback.R clone
   ```
   Copies the current `issue_tracking.xlsx` to `resolutions/<YYYYMMDD>_issues_resolution.xlsx`. A same-day second pass reuses the existing clone rather than discarding in-progress work.
2. List eligible rows:
   ```bash
   Rscript .claude/skills/hfc-agent-skill/scripts/apply_feedback.R list-open
   ```
   Writes `hfc/outputs/fix_candidates.csv` — one row per `Status=Open` + non-empty Comment finding in today's clone, with full context (Issue, Comment, Entity ID, Variable, Value, Issue Category, Issue ID).
3. **Window "Proceed," one tab:** *"Found `<N>` rows with a Comment and Status=Open. I'll interpret each and apply a fix in one pass per row."* — "Proceed with all `<N>` (recommended)" / "Only some of them (I will type in Other)".
4. For **each** eligible row, in turn, in a single pass — interpret the Comment, propose Corrections, apply the fix, and set Status, all at once:
   a. Read its `Issue`, `Comment`, and other fields; decide the concrete technical fix the Comment is asking for (e.g. drop the row, cap a value, recode a field), and draft the Corrections text describing what you did.
   b. Write `hfc/code/resolutions/<Issue ID, sanitized>.R` defining `fix(ds) -> ds` that implements it.
   c. Apply it:
      ```bash
      Rscript .claude/skills/hfc-agent-skill/scripts/apply_feedback.R apply --finding-id "<Issue ID>" --corrections "<what you did>"
      ```
      This loads `<HFC Output Directory>/Updated Data/<stem>.<ext>` if a prior fix already exists (else the original file in the Input Data Directory — never mutated), applies your `fix(ds)`, saves the result back to `<HFC Output Directory>/Updated Data/<stem>.<ext>` (one evolving file, so fixes accumulate), and writes the Corrections text + `Status = Resolved` into today's resolutions clone **only** — `issue_tracking.xlsx` is never touched by this step.
   d. If you can't confidently resolve a row, run `apply_feedback.R needs-review --finding-id "<Issue ID>"` instead — sets `Status = Needs Review` in the clone.
5. Once all rows are handled, fold the clone back into the live file:
   ```bash
   Rscript .claude/skills/hfc-agent-skill/scripts/merge_resolutions.R
   ```
   Writes `merged_issue_resolutions.xlsx` next to `issue_tracking.xlsx` — for matched Issue IDs, Status/Corrections/Correction Author come from today's clone, every other column (in case the field/RA edited something concurrently) comes from the live file untouched; unmatched live rows pass through unchanged.
6. **Window "Commit," one tab:** *"`<N>` rows Resolved, `<M>` Needs Review. This will overwrite the live shared issue_tracking.xlsx."* — "Confirm merge (recommended)" / "Wait, let me review first" (show the row-by-row diff before committing) — then commit:
   ```bash
   Rscript .claude/skills/hfc-agent-skill/scripts/commit_merged_issue_tracking.R merged_issue_resolutions.xlsx
   ```
7. **Rebuild the report — mandatory, every pass:**
   ```bash
   Rscript .claude/skills/hfc-agent-skill/scripts/rebuild_report.R
   ```
   Re-runs M1–M14 against the latest data (`<HFC Output Directory>/Updated Data/` if any fixes were applied, else the original file in the Input Data Directory) using the project's stored config, refreshes the live file's derived **Completion** sheet (that sheet only; Tracking is untouched — the one write to the live file outside `commit_merged_issue_tracking.R`), then drops any finding from the detailed report whose live-tracking Status is now `Resolved`, or whose Issue ID no longer appears in `issue_tracking.xlsx` at all — display-only: the xlsx itself keeps full history unchanged, this only affects what the two reports (`<MMDD>_HFCs.html` and its `detailed/` copy) show. Re-read `hfc/outputs/issues.csv` and redraft both the long Summary narrative (`hfc/config/summary_message.md`) and the condensed message (`hfc/config/summary_condensed.md`) against these fresh findings, same approach as A4 step 7 (post the condensed one in chat), then re-run with `--open`:
   ```bash
   Rscript .claude/skills/hfc-agent-skill/scripts/rebuild_report.R --open
   ```
8. Tell the user which rows were Resolved vs. Needs Review, and that `<HFC Output Directory>/Updated Data/<stem>.<ext>` now holds the latest fixed data (raw unchanged).

## What not to do

- Do not write to the live `issue_tracking.xlsx` before the final Review & Approve gate (A4) is answered "All good!" — every build, first-ever or rebuild alike, produces only a pending `merged_issue_tracking.xlsx` until then.
- Do not overwrite the original microdata file.
- Do not start Pipeline A when the user clearly asked for post-feedback (and vice versa).
- Do not invent access dates, exhibit IDs, or column names that are not in the data.
- Do not skip or silently bypass the config pre-flight check (A0) — if Input Data Directory, HFC Output Directory, or Code Output Directory isn't configured or isn't reachable, stop and direct the user to `install.R` + confirming OneDrive desktop sync is running + editing `config.json`, never proceed with a build that has nowhere to write `issue_tracking.xlsx`.
- Do not show an entity's name anywhere (report or `issue_tracking.xlsx`) unless the user has explicitly set `entity_display: name` in `role_map.yaml` — Entity ID-only is the de-identification default, never overridden silently or by guess.
- Do not require monorepo gold data, `eval/`, `verify_all`, or SimUser for product runs.
- Do not use typed mega-replies (`M1=Y M2=…`) or long option menus as the primary confirmation UX — always guess first, correct if wrong (see Interactive confirms above).
- Do not silently guess the Entity ID without a wrong pick being visibly correctable — it's decided silently by default (A1), but must be nameable and fixable via Deep Review or a free-text correction at the final gate, never truly hidden.
- Do not scatter product dirs outside the Code Output Directory — everything lands under `<Code Output Directory>/hfc/`.
- Do not flag expected skip-logic blanks as missing.
- Do not ignore a specific-check request in the Instructions answer (A1) — every run, every time, match it to a standard module or author an M9 custom check; there's no separate Field Request tab to catch it later.
- Do not infer the data-collection country from the input folder's name/basename — read geography from the data itself.
- Do not let the last date of data collection go unresolved — it's decided silently (A1 step 8/A2 step 5) but must drive the Last Day tab correctly regardless.
- Do not let incomplete/non-surveyed rows leak into M2–M14 once a "status" completion signal has confirmed which rows to filter out.
- Do not run per-row file-hygiene checks for M13 — the only check is a media-indicating column that's completely empty across every surveyed row.
- Do not confuse assent and consent.
- Do not present two near-duplicate variables (e.g. `treat` vs. `treat_ext`) as if they were independently meaningful — silently keep the one most reasonable one.
- Do not hand-edit `issue_tracking.xlsx` (or any tracking-shaped file) via a raw `openxlsx`/direct-write call — use `patch_tracking_cells()` (`scripts/lib/issue_store.R`) for a targeted cell fix. A raw `read.xlsx()`/`writeData()` round trip can silently rewrite the header row to R-sanitized column names, un-mapping every column at once.
